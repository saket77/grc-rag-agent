# Desired features: better JSON chunking and JSON citations

Status: design spike; no implementation choice has been approved.

Last researched: 2026-09-26.

## Problem

The JSON pipeline needs two related improvements:

1. Create useful, size-bounded embedding documents from both ordinary and nested JSON without
   separating facts from the context that gives them meaning.
2. Return a JSON citation that identifies the source more precisely than `page: null` plus a whole
   retrieved chunk.

These are separate concerns. Chunking determines what is embedded and retrieved. Citation metadata
must identify where retrieved evidence came from, but must not be trusted merely because it was
embedded or generated by the answer model.

## Current behavior

- A root JSON object becomes one normalized LangChain `Document`.
- Items in a root JSON array become separate documents, with their original array indices retained
  in metadata even when empty items are skipped.
- `RecursiveCharacterTextSplitter` then splits each document and adds `start_index` metadata.
- Document embeddings currently use only `chunk.page_content`; arbitrary metadata does not affect
  retrieval.
- The current answer flow lets the model select retrieved chunk IDs, after which the server resolves
  those IDs to source-owned citations. For JSON, the citation still has `page: null` and a coarse
  whole-chunk excerpt.

## What existing libraries actually provide

### LangChain JSONLoader

[`JSONLoader`](https://reference.langchain.com/python/langchain-community/document_loaders/json_loader/JSONLoader)
uses a caller-supplied `jq_schema` to select records. Each selected value becomes a `Document`, and a
`metadata_func` can add record metadata. This is useful when the JSON schema is known, but it does
not automatically discover the correct record boundary for arbitrary uploaded JSON.

### LangChain RecursiveJsonSplitter and `create_documents`

[`RecursiveJsonSplitter`](https://reference.langchain.com/python/langchain-text-splitters/json/RecursiveJsonSplitter)
walks nested dictionaries, tries to preserve hierarchy, and can convert lists into dictionaries
whose keys are array indices. Its
[`create_documents`](https://reference.langchain.com/python/langchain-text-splitters/json/RecursiveJsonSplitter/create_documents)
method calls the JSON splitter, serializes each resulting dictionary, and wraps each string in a
LangChain `Document` with copied metadata.

That method creates valid `Document` objects, but it does not by itself:

- infer which nested arrays are logical records;
- split a single oversized string reliably;
- guarantee that parent context is repeated in every later chunk;
- attach a citation range to the uploaded or normalized source.

A local experiment used the concrete `organization + pages[]` example with
`max_chunk_size=1000`. With `convert_lists=False`, the installed splitter returned one 2,064-character
chunk. With `convert_lists=True`, it returned chunks of 2,025 and 60 characters, and the later chunk
did not retain `organization`. Therefore, adopting `create_documents` directly must remain a tested
candidate rather than an assumption.

### Existing precedent for character ranges

LangChain's base
[`TextSplitter`](https://reference.langchain.com/python/langchain-text-splitters/base/TextSplitter)
supports `add_start_index=True`, which this repository already enables.

LlamaIndex implements the same broader idea in its
[`NodeParser` post-processing](https://github.com/run-llama/llama_index/blob/main/llama-index-core/llama_index/core/node_parser/interface.py):
it finds each node's content in the parent document and stores `start_char_idx` and `end_char_idx`.
This is a useful precedent for source ranges, but duplicate text, overlapping chunks, normalization,
and node ordering still require explicit tests.

If exact positions in the original uploaded bytes eventually become a requirement, Tree-sitter
nodes expose byte ranges and row/column positions, and an official
[`tree-sitter-json`](https://github.com/tree-sitter/tree-sitter-json) grammar exists. That would add a
second parser and more complexity, so it is not the default proposal.

## Desired JSON chunking behavior

Treat JSON ingestion as two stages rather than asking one splitter to solve everything:

1. **Choose logical records.** Preserve current root-object and root-array behavior. Evaluate a
   conservative rule for nested arrays of objects such as `pages`, `sections`, `controls`, or
   `findings`. Keep scalar arrays such as `providers: ["AWS", "Azure"]` together.
2. **Apply a hard size bound.** After record selection, split oversized serialized records or long
   text fields with a text splitter that actually enforces the configured chunk limit.

Parent fields such as organization, report title, section title, or control family may be useful for
retrieval. Storing them only in metadata is insufficient because this application embeds
`page_content`. A candidate implementation should deliberately construct an embedding input from
bounded parent context plus source chunk text while keeping source text and provenance separately
available for citation validation.

No generic record-detection heuristic should ship merely because it works for a key named `pages`.
It must be compared against known examples first.

## Desired JSON citation behavior

JSON Pointer is not the preferred user-facing design. The leading candidate is a server-computed
range within the exact normalized JSON record that was chunked:

```json
{
  "page": null,
  "excerpt": "The production service is hosted on AWS.",
  "json_location": {
    "record": 1,
    "start_char": 1842,
    "end_char": 1887
  }
}
```

The proposed range contract is:

- zero-based and end-exclusive;
- measured in Unicode characters;
- relative to one explicitly identified normalized JSON record;
- computed by the server from trusted chunk metadata and source text;
- never supplied by the answer model;
- valid only when `normalized_record[start_char:end_char] == excerpt`.

Candidate chunk metadata:

```python
{
    "source_type": "json",
    "record": 1,
    "start_index": 1400,
    "end_index": 2200,
}
```

The existing splitter already supplies `start_index`. The end can be derived from the chunk length.
If a citation later narrows from the whole chunk to a server-selected excerpt, its absolute record
range can be calculated from the chunk start plus the excerpt's verified local position.

This proposal intentionally distinguishes:

- **embedding text**, which may include bounded context for retrieval quality;
- **source text**, which must remain available for citation verification; and
- **location metadata**, which is provenance and should never be embedded as proof.

## Decision spike before implementation

Build an offline comparison rather than immediately replacing ingestion. Compare at least:

1. Current normalization plus `RecursiveCharacterTextSplitter`.
2. `RecursiveJsonSplitter.create_documents` with and without list conversion.
3. A small hybrid prototype: logical-record extraction followed by the existing text splitter.

Use the same fixtures and questions for every candidate:

- a small root object;
- a root array with empty items and preserved original indices;
- `organization + pages[]` with a long text field whose answer is near the end;
- scalar arrays that must stay together;
- two records containing identical text;
- repeated excerpts within one record;
- Unicode, including characters outside the BMP;
- keys and values containing quotes, slashes, tildes, and escaped characters;
- empty lists, empty strings, null, false, and zero as evidence;
- inputs near extracted-character and chunk-count limits.

Record these results:

- chunk count and serialized size of every chunk;
- whether each chunk remains within the configured bound;
- whether required parent context reaches the embedding input;
- retrieval recall at `k` for a fixed labeled question set;
- exact record identity for retrieved chunks;
- whether every citation satisfies the source-slice invariant;
- duplicate/overlap behavior;
- expanded characters and estimated embedding tokens;
- elapsed retrieval time and provider-call count.

Deterministic fake embeddings can verify plumbing and provenance. They cannot establish semantic
retrieval quality; that needs a small, explicitly run evaluation using the configured embedding
provider and permitted synthetic or public documents.

## Acceptance gates

Do not select an implementation until it demonstrates all of the following:

- no regression for existing root objects, root arrays, PDFs, limits, or abstention;
- hard chunk-size enforcement, including very long JSON string values;
- better retrieval of nested evidence on the fixed evaluation set;
- bounded repetition of parent context;
- server-owned citations with an exact, tested source location;
- deterministic behavior for duplicate text and overlapping chunks;
- no model-generated path, page number, range, or excerpt treated as authoritative.

## Out of scope for the same change

- Folder reorganization.
- Batched answer generation.
- Cross-request document caching.
- A second JSON parser solely for original-byte highlighting, unless normalized-record ranges prove
  insufficient.
